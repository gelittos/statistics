Homework 02

From Wallet Seed to Ethereum Address

Hashing, key derivation and cryptographic primitives.

Assigned 8 October 2016

From recovery words to an address

This report examines a common Ethereum wallet workflow based on BIP-39, BIP-32 and BIP-44. These standards describe wallet key management; Ethereum itself does not require every wallet to use a mnemonic or this particular derivation path.

We consider an externally owned account controlled by a private key. Contract addresses follow different creation rules.

  1. Generate random entropy.
  2. Encode entropy and a checksum as a BIP-39 mnemonic.
  3. Derive a seed from the mnemonic and an optional passphrase.
  4. Derive a private key using BIP-32 and a BIP-44 path.
  5. Compute the public key using secp256k1.
  6. Hash the public key with Keccak-256 and retain 20 bytes.
  7. Apply the EIP-55 mixed-case checksum.

A mnemonic, a seed, a private key, a public key and an address are different objects. In particular, an address is not a public key, and a mnemonic is not the final binary seed.

1. BIP-39: mnemonic and seed

From randomness to words

The starting point is securely generated random entropy. BIP-39 supports 128, 160, 192, 224 or 256 bits of entropy, corresponding to 12, 15, 18, 21 or 24 words.

A checksum is obtained from the first ENT / 32 bits of SHA-256(entropy), where ENT is the entropy length. The checksum is appended to the entropy. The resulting bits are divided into groups of 11, each selecting one word from a list of 2048 words.

For example: 128 entropy bits + 4 checksum bits = 132 bits. Dividing by 11 gives a 12-word mnemonic. The checksum helps detect mistakes; it adds no new entropy.

From words to a seed

PBKDF2-HMAC-SHA512 uses the mnemonic as its password and "mnemonic" followed by the optional passphrase as its salt. Both strings use UTF-8 with NFKD normalization. With 2048 iterations, it produces a 512-bit seed.

An absent passphrase is an empty string. Changing the passphrase produces a different wallet seed. This passphrase is distinct from an application's local password used to unlock its stored wallet data.

2. BIP-32: a tree of keys

A hierarchical deterministic wallet derives a tree of keys from one seed. "Deterministic" means that the same seed and path reproduce the same keys.

The master step computes HMAC-SHA512 with the fixed string "Bitcoin seed" as its key and the seed as its data. The left 32 bytes provide the candidate master private key; the right 32 bytes provide the chain code. Invalid master key values must be rejected.

The chain code is additional derivation data used together with a parent key and a child index. Child derivation uses HMAC-SHA512 and arithmetic modulo the curve subgroup order. It also defines how invalid child results are handled.

Non-hardened derivation allows child public keys to be obtained from an extended public key, without private keys. Hardened derivation requires parent private-key material. A prime symbol in a path marks a hardened level.

3. BIP-44: choosing a path

BIP-44 organizes the BIP-32 tree. It is a path convention, not a separate hashing or encryption algorithm. Its general structure is:

m / purpose' / coin_type' / account' / change / address_index

A common Ethereum path is:

m/44'/60'/0'/0/0

  • m: the master private node.
  • 44': the BIP-44 purpose.
  • 60': the Ethereum coin type.
  • 0': the first account.
  • 0: the external-address branch.
  • 0: the first address index.

Changing the final index selects another child key. Wallet implementations may use different account-discovery conventions or paths. Recovering the intended account requires the correct mnemonic, passphrase and path.

4. secp256k1: the public key

The derived private key is a scalar k in the valid range 1 to n − 1, where n is the order of the secp256k1 base point. Its public key is Q = kG.

This is the same mathematical relationship explored in Homework 1, but with cryptographic-size parameters. The public key is a curve point with coordinates x and y.

secp256k1 supplies the curve used for Ethereum's ECDSA signatures. The private key signs; the public key is used to verify signatures. Computing the public key is not itself signing, hashing or encryption.

5. Keccak-256: the address

Encode x and y as two 32-byte, big-endian values and concatenate them. Hash these 64 bytes using Keccak-256. If starting from the 65-byte uncompressed public-key encoding, omit its initial 0x04 format byte.

Keccak-256 produces 32 bytes. The Ethereum address consists of its final 20 bytes, or 160 bits. Hexadecimal encoding represents those bytes using 40 characters, usually preceded by "0x".

Hash the public-key bytes, not their hexadecimal text. Ethereum uses Keccak-256, which is different from standardized SHA3-256.

6. EIP-55: the checksum

EIP-55 adds error-detection information through the letter case of the hexadecimal address. It does not change the underlying 20-byte address.

  1. Write the address as 40 lowercase hexadecimal characters, without the "0x" prefix.
  2. Compute Keccak-256 of that text using its ASCII/UTF-8 bytes.
  3. For each address letter a–f, inspect the hash hexadecimal digit at the same position. Use uppercase if its value is at least 8; otherwise keep lowercase.
  4. Leave numeric characters unchanged and restore "0x".

A validator can recompute this pattern to detect many typing errors. The checksum does not prove ownership or protect against someone deliberately replacing an address with another correctly checksummed address.

Different tools, different purposes

Roles in the wallet pipeline
Concept Purpose Example
Key generation Establish fresh secret material using secure randomness. Initial random entropy for the wallet.
Key derivation Reproducibly obtain key material from an existing secret. BIP-39 seed derivation and BIP-32 child derivation.
Public-key cryptography Support signatures with related private and public keys. ECDSA using secp256k1.
Hashing Compute a fixed-length digest. Keccak-256 in address derivation.
Checksum Detect accidental errors. BIP-39 checksum bits and EIP-55 letter case.
Encoding Represent data in another reversible format. Binary groups as words; address bytes as hexadecimal.

Several primitives are needed because the tasks are different. A mnemonic makes backup easier, a derivation scheme organizes keys, public-key cryptography supports signatures, hashing produces an address digest, and a checksum helps detect errors. Encoding makes data readable but does not encrypt it.
